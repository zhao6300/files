01 / WHY SLO

SLA、SLO、SLI：三个词，一条闭环

把承诺、目标和实际测量分开，才能让性能讨论可执行。

SLA

对外承诺

服务在什么范围内应达到怎样的体验

纸面上的服务等级协议

SLO

内部目标

我们为用户体验设置的可衡量阈值

例如：TTFT、TPOT 的目标线

SLI

实际指标

系统真实运行时采集到的表现

例如：p95 TTFT、SLO 达成率

共同语言的价值：每次优化，都能明确回答“影响的是承诺、目标，还是实际测量？”

02 / THE TWO MOMENTS

TTFT 与 TPOT：同一条回答里的两种度量

一个关注“开始得快不快”，一个关注“持续得顺不顺”。

TTFT

时间

首 token 出现前的完整等待

从请求到达开始，包含排队、调度、KV 获取、Prefill、传输等步骤。

TPOT

每个 token 的时间

生成过程的平均步长

进入 Decode 后，相邻输出 token 之间的平均间隔；越稳定，阅读越流畅。

TTFT = 排队 + 调度 + KV 获取 + Prefill + 传输　｜　TPOT ≈ Decode 总时间 ÷（输出 token 数 − 1）

02 / THE TWO MOMENTS

Goodput：满足体验约束后的“有效服务量”

吞吐最高，不一定等于用户体验最好；真正有效的是同时满足两个 SLO 的请求。

Goodput = 在 TTFT 与 TPOT 都达标的前提下，单位时间内成功服务的请求数

吞吐提升

资源更满

排队 / 干扰增加

体验波动

SLO 达成率下降

有效服务量

Goodput 可能下降

核心判断：不是“设备忙不忙”，而是“用户体验达标的请求有多少”。

04 / SUSTAINED GENERATION

Chunked Prefill：一个典型的 TTFT ↔ TPOT 旋钮

切得更大或更小，都不是绝对更好，而是在两种体验之间重新分配资源。

Prefill 更连续

大 Chunk

TTFT 通常更好　·　TPOT 风险更高

更频繁让出资源

小 Chunk

TPOT 通常更稳　·　TTFT 风险更高

管理原则：根据当前 SLO 压力动态选择 Chunk，而不是固定一个“最优值”。

调度：谁先服务，决定谁还有机会达标

05 / SYSTEM CHOICES

Latency Budget：把“还有多少时间”变成共同语言

同一个 KV 搬运、同一次排队，对不同请求的风险完全不同。

Request ATTFT SLO 5.0s

已花 1.0s

剩余 4.0s

Request BTTFT SLO 5.0s

已花 4.5s

剩余 0.5s

一个 300ms 的 KV transfer

对 Request A　还有足够余量，可以接受

对 Request B　会显著增加违约风险，应优先处理

因此调度、KV movement、抢占等操作，应该共同消耗并参考这个预算。
